# 📚 Database Migrations Explained - Complete Guide

## 🎯 Overview: How Database Changes Work from Local to Production

This document explains **exactly** how database migrations work in your project, from making changes on your local computer to deploying them safely to production **without losing any production data**.

---

## 🔐 Key Concept: Separate Databases

### Your Setup

```
┌─────────────────────────────────────────────────────────────┐
│  LOCAL COMPUTER (Your Development Machine)                  │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ Database: localhost:5432/stemtoys_dev               │   │
│  │ - You can experiment here safely                    │   │
│  │ - Resetting this database is OK                     │   │
│  │ - No real customer data                             │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  PRODUCTION (Live Website - Vercel/Railway)                │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ Database: neon.tech or railway.app (cloud)          │   │
│  │ - Real customer data (orders, users, products)      │   │
│  │ - NEVER reset this database                         │   │
│  │ - Protected by backups                              │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

**Important**: These are **TWO COMPLETELY SEPARATE DATABASES**. Changes on your local computer **DO NOT** affect production automatically.

## 📋 Complete Workflow: From Local Change to Production

### Step 1: Make Changes on Your Local Computer

**File**: `prisma/schema.prisma`

You edit the schema file to add a new column or table:

```prisma
model User {
  id        String   @id @default(cuid())
  email     String   @unique
  name      String?
  
  // 👇 YOU ADD THIS NEW FIELD
  phoneNumber String?  // New field you want to add
  createdAt DateTime @default(now())
}
```

**What happens**: 
- ✅ You've only changed a file on your computer
- ✅ Production database is **untouched**
- ✅ Nothing has changed in production yet

---

### Step 2: Create a Migration Locally

**Command**:
```bash
# IMPORTANT: Ensure you're using LOCAL database
export DATABASE_URL="postgresql://postgres:postgres@localhost:5432/stemtoys_dev"

# Create the migration
npx prisma migrate dev --name add_user_phone_number
```

**What happens internally**:

```
1. Prisma reads your schema.prisma file
2. Compares it to your LOCAL database structure
3. Generates SQL commands to make them match
4. Creates a migration file: prisma/migrations/20250115_add_user_phone_number/migration.sql
5. Applies those SQL commands to your LOCAL database
6. Updates Prisma Client (code that talks to database)
```

**Migration file created** (`prisma/migrations/20250115_add_user_phone_number/migration.sql`):

```sql
-- Migration automatically generated by Prisma
ALTER TABLE "User" ADD COLUMN "phoneNumber" TEXT;
```

**What happened**:
- ✅ Migration file created in `prisma/migrations/` folder
- ✅ Your **LOCAL** database now has the new column
- ✅ Production database **still unchanged**
- ✅ Migration file is ready to be applied to production later

### Step 3: Test Locally

**Commands**:
```bash

pnpm run build
```

**What you verify**:
- ✅ Application runs with new schema
- ✅ No errors in console
- ✅ New field works as expected
- ✅ Existing functionality still works

---

### Step 4: Review Migration SQL (Critical Safety Check)

**Command**:
```bash
# View what will run in production
cat prisma/migrations/20250115_add_user_phone_number/migration.sql
```

**What to check**:

✅ **SAFE** - These are good:
```sql
ALTER TABLE "User" ADD COLUMN "phoneNumber" TEXT;  -- Adding column (safe)
CREATE TABLE "Wishlist" (...);                     -- Creating table (safe)
CREATE INDEX "User_phone_idx" ON "User"("phone");  -- Adding index (safe)
```

❌ **DANGEROUS** - If you see these, STOP:
```sql
DROP TABLE "User";                          -- Deleting table (dangerous!)
ALTER TABLE "User" DROP COLUMN "email";     -- Removing column (dangerous!)
DELETE FROM "User";                         -- Deleting data (dangerous!)
```

**Why this matters**: You need to verify that the migration **only adds** things, never **removes** things from production.

---

### Step 5: Backup Production Database

**Command**:
```bash
pnpm run backup:production
```

**What happens**:
- ✅ Creates a complete backup of production database
- ✅ Saved as: `backups/backup_production_TIMESTAMP.sql.gz`
- ✅ Can restore production if something goes wrong
- ✅ Safety net in case migration has unexpected issues

**Important**: Always do this before deploying database changes!

### Step 7: Production Deployment (Automatic)

**What Vercel/Railway Does Automatically**:

When you push to GitHub, the deployment platform automatically:

```
1. Clones your code from GitHub
2. Installs dependencies (pnpm install)
3. Generates Prisma Client (prisma generate)
4. Runs migrations (prisma migrate deploy)  ← THIS APPLIES YOUR MIGRATION
5. Builds your Next.js app (next build)
6. Deploys to production servers
```

**The Migration Command** (`prisma migrate deploy`):

This command:
1. Connects to **PRODUCTION** database (not local!)
2. Checks which migrations have already been applied
3. Finds new migrations (like yours) that haven't been applied
4. Runs them **one by one** in order
5. Updates tracking table to remember what's been applied

**Example deployment log**:

```

✓ Installing dependencies
✓ Generating Prisma Client
Running database migrations...
  → Checking migration status...
  → Found 1 new migration: 20250115_add_user_phone_number
  → Applying migration to production database...
  ✓ Migration applied successfully
  → Production database now matches schema
✓ Building Next.js application
✓ Deployment successful
```

**What happens to production data**:

```

├─────────────────────┤
```

- ✅ New column added with NULL for existing rows

- ✅ New users can fill in phoneNumber when registering

## 🔒 Why Production Data is Safe

### Safety Mechanisms

1. **Separate Databases**
   - Local database ≠ Production database
   - Changes locally don't affect production until you push

2. **Migration Tracking**
   - Prisma tracks which migrations have been applied
   - Same migration never runs twice
   - Migrations run in order

3. **Additive Changes Only**
   - Adding columns/tables never deletes existing data
   - Existing rows get NULL or default values for new columns
   - No DROP TABLE or DROP COLUMN in safe migrations

4. **Backups**
   - Production database backed up before changes
   - Can restore if something goes wrong

5. **Testing First**
   - Changes tested locally before production
   - Migration SQL reviewed before deployment

## 🎬 Real-World Example Walkthrough

### Scenario: Adding a "Wishlist" Feature

Let's walk through adding a complete new feature with a new table.

#### Step 1: Update Schema Locally

**File**: `prisma/schema.prisma`

```prisma
// Add new Wishlist model
model Wishlist {
  id        String   @id @default(cuid())
  userId    String
  productId String
  createdAt DateTime @default(now())
  
  user    User    @relation(fields: [userId], references: [id])
  product Product @relation(fields: [productId], references: [id])
  
  @@unique([userId, productId])
}

// Add relation to existing User model
model User {
  id          String     @id @default(cuid())
  email       String     @unique
  wishlist    Wishlist[]  // ← NEW relation
  // ... rest of fields
}

// Add relation to existing Product model
model Product {
  id          String     @id @default(cuid())
  name        String
  wishlist    Wishlist[]  // ← NEW relation
  // ... rest of fields
}
```

#### Step 2: Create Migration Locally

```bash
export DATABASE_URL="postgresql://postgres:postgres@localhost:5432/stemtoys_dev"
npx prisma migrate dev --name add_wishlist_table
```

**Output**:
```
✓ Created migration: 20250115_add_wishlist_table
✓ Applied migration to database
✓ Generated Prisma Client
```

**Migration file** (`prisma/migrations/20250115_add_wishlist_table/migration.sql`):

```sql
-- CreateTable
CREATE TABLE "Wishlist" (
    "id" TEXT NOT NULL,
    "userId" TEXT NOT NULL,
    "productId" TEXT NOT NULL,
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    CONSTRAINT "Wishlist_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE UNIQUE INDEX "Wishlist_userId_productId_key" ON "Wishlist"("userId", "productId");

-- AddForeignKey
ALTER TABLE "Wishlist" ADD CONSTRAINT "Wishlist_userId_fkey" 
  FOREIGN KEY ("userId") REFERENCES "User"("id") ON DELETE CASCADE ON UPDATE CASCADE;

ALTER TABLE "Wishlist" ADD CONSTRAINT "Wishlist_productId_fkey" 
  FOREIGN KEY ("productId") REFERENCES "Product"("id") ON DELETE CASCADE ON UPDATE CASCADE;
```

**What this does**:
- ✅ Creates new `Wishlist` table
- ✅ Does NOT modify User or Product tables (only adds relations)
- ✅ All existing users and products remain unchanged

#### Step 3: Test Locally

```bash
pnpm run dev
# Test wishlist feature works
# Create wishlist items
# Verify existing users/products still work
```

#### Step 4: Review Migration

```bash

```

**Verification**:
- ✅ Only CREATE TABLE statements (safe)
- ✅ No DROP TABLE statements (good!)
- ✅ No DELETE statements (good!)
- ✅ Safe to deploy

**Output**:

## 🚫 What NEVER Happens (Safety Guarantees)

### Production Data is NEVER:

1. **Deleted**: Adding columns/tables never deletes existing data
2. **Overwritten**: Existing data remains unchanged
3. **Modified**: Your migration doesn't change existing values
4. **Lost**: Backups protect against accidental issues

### Safe Migration Operations:

✅ **Always Safe**:
- `ALTER TABLE ... ADD COLUMN` - Adds new column
- `CREATE TABLE` - Creates new table
- `CREATE INDEX` - Adds performance index
- Adding relations (foreign keys)

❌ **Potentially Dangerous** (requires special handling):
- `DROP TABLE` - Deletes entire table
- `ALTER TABLE ... DROP COLUMN` - Removes column and data
- `DELETE FROM` - Deletes rows
- Making columns required without defaults

## 📊 Migration Tracking System

### How Prisma Knows What's Applied

Prisma maintains a special table in your database:

```
_prisma_migrations Table:
┌─────────────────────────────────────────────────────┐
│ migration_name          | applied_at                │
├─────────────────────────────────────────────────────┤
│ 20240101_initial        | 2024-01-01 10:00:00      │
│ 20240115_add_phone      | 2024-01-15 14:30:00      │
│ 20240201_add_wishlist   | 2024-02-01 09:15:00      │
│ 20250115_add_phone_num  | (not applied yet)        │ ← Your new migration
└─────────────────────────────────────────────────────┘
```

**When you deploy**:

1. Prisma checks `_prisma_migrations` table
2. Compares with migration files in `prisma/migrations/`
3. Finds migrations not yet applied (like yours)
4. Runs them in chronological order
5. Records them in `_prisma_migrations` table

**Why this is safe**:
- ✅ Same migration never runs twice
- ✅ Migrations run in correct order
- ✅ Can track migration history
- ✅ Can identify if migrations are missing

## 🔄 What Happens if Migration Fails?

### Automatic Rollback

If a migration fails partway through:

```
Migration starts...
  → Creating table... ✓
  → Adding column... ✗ ERROR: Column already exists

Migration rolled back automatically
→ All changes from this migration undone
→ Database in previous safe state
→ Deployment fails (prevents broken state)
```

**Prisma handles this automatically** - if migration fails, it rolls back all changes from that migration.

### Manual Recovery

If you need to fix a failed migration:

```bash
# 1. Check what went wrong in deployment logs
# 2. Fix the issue locally
# 3. Create a new migration with the fix
npx prisma migrate dev --name fix_migration_issue

# 4. Test locally
# 5. Deploy again
git push origin main
```

## ❓ Common Questions

### Q: What if I make a mistake in the schema?

**A**: If you catch it before pushing to production:
- Just edit the schema again
- Create a new migration
- Test locally
- Deploy when ready

If you already pushed but migration hasn't run:
- Create a new migration to fix it
- Deploy the fix

### Q: Can I delete a column from production?

**A**: Yes, but requires special handling:
1. Don't do it in one step (data loss!)
2. First: Mark column as deprecated in code
3. Then: Create migration to remove column (after users migrate)
4. Always backup first

### Q: What if migration fails in production?

**A**: 
- Prisma automatically rolls back the failed migration
- Your database stays in previous safe state
- Deployment fails (prevents broken app)
- Fix the issue and create new migration
- Deploy again

### Q: Can I run migrations manually?

**A**: Yes, but usually not needed:
```bash
# Connect to production database
export DATABASE_URL="your_production_database_url"

# Apply pending migrations
npx prisma migrate deploy
```

### Q: How do I see what migrations have been applied?

**A**:
```bash
# Check migration status
npx prisma migrate status

# Or check the _prisma_migrations table directly
```
